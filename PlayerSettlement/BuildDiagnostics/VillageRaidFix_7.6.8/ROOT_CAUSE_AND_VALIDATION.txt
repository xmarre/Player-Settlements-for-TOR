Player Settlements 7.6.8 village raid and siege integration fix

SYMPTOM 1
Beginning a raid against a dynamically created player village can terminate the game with a native access violation.

OBSERVED TRIGGER
The supplied report fails in:
ManagedCallbacks.ScriptingInterfaceOfIMBMapScene.TickVisuals
TaleWorlds.MountAndBlade.MBMapScene.TickVisuals
SandBox.View.Map.MapScreen.TickVisuals

MBMapScene.TickVisuals forwards native pointers from MapScreen's ticked Mesh array. This failure class means at least one wrapper in that array no longer refers to a valid native mesh when the frame is rendered. Raid initialization changes the village state to BeingRaided and marks the settlement party's level mask dirty, which causes the map visual to rebuild.

CONTRIBUTING IMPLEMENTATION
The TOR visual compatibility helper created generated settlement visuals with:
GameEntity.CopyFrom(scene, source, true, false)

The source was an already-live campaign-map settlement entity. That copied mutable map entity/component/level-mask state rather than creating a clean instance of the underlying prefab.

ROOT-CAUSE PATCH
The helper now uses:
GameEntity.CopyFromPrefab(source)

The generated entity remains same-culture, retains its generated ID and position, and receives independent prefab-backed native state. The prior workaround of removing map visuals is not used.

SYMPTOM 2
Hostile lords approach a custom town or castle, fail to start a siege, and leave. Armies are not formed to attack those fortifications.

ROOT CAUSE
The generated settlement XML already supplies the player clan as owner. BuildCastle/BuildTown then assigned the same clan again. TaleWorlds.CampaignSystem.Settlements.Town.OwnerClan returns immediately when the value is unchanged.

That bypasses Town.ChangeClanInternal -> SetNewOwnerClan -> Clan.OnFortificationAdded. Consequently the custom fortification is absent from Clan._fiefsCache and Clan._settlementsCache, and from the corresponding kingdom caches. Native AiMilitaryBehavior enumerates IFaction.Settlements when scoring military targets, so the settlement is not available as a strategic siege target.

VIOLATED INVARIANT
Every fortification with a non-null OwnerClan must appear exactly once in that clan's and kingdom's official fortification/settlement caches.

SIEGE PATCH
- Newly built custom towns and castles now transition OwnerClan from null to Clan.PlayerClan. This invokes the official remove/add lifecycle and populates all native caches.
- Existing player-owned generated fortifications bound to generated villages receive the same null -> PlayerClan transition once when the campaign session launches.
- A fortification owned by another clan is left unchanged, preventing conquered settlements from being reclaimed by the repair.

RETAINED 7.6.7 REPAIRS
The one-shot session repair still restores missing generated-village component owner, bound-settlement validation, and castle-village trade-bound references. No recurring tick scan was added.

ALTERNATIVE HYPOTHESES CHECKED
- The village crash is not a managed null-reference failure in raid logic; the supplied stack terminates inside native map visual ticking.
- The siege issue is not caused only by party pathfinding or scene availability. Native military target enumeration depends on faction settlement caches, and the identical OwnerClan assignment provably skips the cache-populating lifecycle.
- The existing 7.6.7 condition repaired only OwnerClan == null. It could not repair a non-null owner whose native caches were never populated.

STATIC VALIDATION
- PlayerSettlementCultureVisuals.dll resolves GameEntity.CopyFromPrefab with the correct one-argument signature.
- BuildCastle and BuildTown contain null -> Clan.PlayerClan owner transitions before settlement initialization finishes.
- Existing-save repair handles null owners and re-registers only current PlayerClan ownership; non-player ownership branches around the transition.
- Modified method branch targets resolve to instruction boundaries.
- BuildTown's exception-handler try/handler offsets were adjusted for the two-byte IL insertion.
- Win64 and Gaming.Desktop.x64 copies are byte-identical.
- Runtime verification is still required because native engine lifetime and AI decision behaviour cannot be executed here.
